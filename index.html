Satellite Pass Predictor

Predict when a satellite is visible from your location — built on real orbital physics (SGP4) — plus a data-science study of how the predictions decay over time.

The product — a pass-prediction app

An interactive Streamlit dashboard: pick your city, choose a satellite, and get every upcoming visible pass (rise → peak → set) across six tabs — a pass table, elevation-over-time, a polar sky view, a ground track, a 3-D globe, and a plain-English Summary that explains, step by step, how the prediction is made. Pure physics (SGP4), live orbital data, 41 passing tests.

Run it locally: pip install -r requirements.txt then streamlit run app.py. (A live hosted demo can be added via Streamlit Community Cloud.)

The data science

The app is physics; the data science is how I understand and stress-test it. I collected real orbital history from the Space-Track API and asked two questions — one a regression, one a classification.

Study 2 — Classification: “is this TLE too stale to trust?”

Supervised binary classification on 32,540 real measurements from 5 satellites (altitudes ~420–870 km). Target: is the prediction error > 10 km? Four models compared on a held-out stratified test set.

The Random Forest flags stale data with 96.3% accuracy and ROC-AUC 0.99, and its feature importance matches the physics — TLE age and orbital altitude (drag) dominate. → read the full notebook.

Study 1 — Regression: how fast does accuracy decay?

180 days of ISS data; 11,267 measurements of (TLE age → error in km).

  • Error grows from <1 km when fresh to ~55 km after a week (~7 km/day).
  • The average trend is highly predictable (R² = 0.98); a single prediction’s error is not (R² = 0.08) — it’s dominated by space weather.
  • A naïve baseline actually beat the model on individual predictions (19.8 vs 23.7 km MAE) — so the honest fix is to refresh the data, which is what the app does.

What this project demonstrates

  • Data acquisition from a live API, and building clean, reproducible datasets.
  • Both problem types — regression and classification — with the right metrics for each (R²/MAE vs accuracy/recall/ROC-AUC).
  • Model comparison against a baseline, handling imbalanced classes, and interpretable results.
  • Judgment: knowing when not to use ML (physics beat it for the core prediction).
  • Shipping a real, tested, documented product.
